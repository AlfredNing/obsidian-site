# 第二大脑操作手册

> 这个库存在的唯一目的：**让我在遇到问题时，能比自己裸脑多想一步。**
> 如果一篇笔记从来没有在决策、行动或创作中被打开过，它就是一块占空间的石头。

---

## 〇、一条铁律

**写不出「我在什么场景下会用到这个」，就不写。**

这不是建议，是门槛。过不了这个门槛的内容，让它留在浏览器标签页里——它还没有重要到值得占用你未来翻笔记时的注意力。

---

## 一、先搞清楚：什么不是第二大脑

| 第二大脑 **不是** | 第二大脑 **是** |
|---|---|
| 收藏夹的备份 | 遇到问题时第一个翻的地方 |
| 教科书摘抄本 | 我自己踩坑、判断、决策的记录 |
| 分类完美的档案馆 | 能顺着链接找到相关思考的网络 |
| 越整理越爽的玩具 | 用起来省时间的工具 |

**核心区别：收藏家存信息，思考者存经历。**

大脑不会记住"信息"，只记住"经历"。抄写一遍 RAG 的定义不算经历；用 RAG 解决了一个检索不准的问题、把踩坑过程写下来——这才是经历，才会被记住。

---

## 二、笔记与知识体系：别把工具当目标

### 你不需要"建立知识体系"

"建立知识体系"这五个字本身就是一个陷阱。它让你觉得有一个终点——等笔记整理好了、链接建好了、MOC 画好了，就"有了"一个知识体系。

没有哪个真正厉害的人是"先建好知识体系，再用它做事"的。**他们都是先做事，做着做着，脑子里自然长出了结构。**

### 真实的关系

大多数人以为的关系：

```
记笔记 → 积累笔记 → 整理笔记 → 形成知识体系 → 用知识体系做事
```

**真实的关系是反过来的：**

```
遇到问题 → 思考 → 行动 → 复盘 → 笔记是副产品
                                → 知识体系也是副产品
```

**笔记和知识体系，都是"反复解决问题"的副产品。** 它们不是目标，不是手段，是结果。

### 知识体系像一棵树

你不可能"建"一棵树。你能做的是：

- 种一颗种子（遇到一个真实问题）
- 浇水施肥（围绕这个问题思考、行动、踩坑）
- 树自己会长出来（知识体系自然形成）

**笔记是树上掉下来的叶子。** 叶子不是树，但叶子多了，能看出这棵树的形状。

之前的做法是**捡别人的叶子，试图拼成一棵树**——100 片叶子堆在一起，不是树，是落叶堆。

### 知识体系到底是什么？

**知识体系 = 你解决过的问题之间的关系网。**

不是一堆概念的分类表，而是：

> "我做过 A，踩了坑 X，发现跟 B 有关，后来又用 B 解决了 C 的问题。"

这个东西**只存在于脑子里**，不在 Obsidian 里。Obsidian 里记的，只是这个过程中值得记的片段。

### 笔记的三个作用

1. **帮你思考**（最重要的）——写的过程就是思考的过程。写不出来说明还没想清楚。笔记是思考的工具，不是思考的结果。
2. **帮未来的自己回忆**——三个月后忘了当时为什么选 512 tokens 的 chunk 大小，翻笔记想起来了。笔记是记忆的外挂，不是知识的仓库。
3. **帮别人理解你**——一篇踩坑记录，同事看了少走两天弯路。笔记是经验的传递，不是信息的搬运。

### 一句话

> **别把工具当目标。持续解决真实问题，偶尔把值得记的写下来。知识体系自己会长出来。**

## 三、写笔记之前：三道硬门槛

每次想新建或编辑一篇笔记，**依次**回答：

### 门槛 1：场景
> **我在什么场景下会需要这个？**

- 答不出来 → **停。不写。**
- 答得出来 → 进入下一关

### 门槛 2：加工
> **我能不能用自己的话，把这个东西的核心讲清楚？**

- 只能照搬原文 → **停。你还没消化。**
- 能用自己的话说 → 进入下一关

### 门槛 3：连接
> **它跟我已有的哪个知识/经验/项目有关？**

- 找不到任何连接 → **先写下来，标记 `#待连接`，一周内必须找到连接或删除。**
- 能找到 → 写进笔记，用 `[[链接]]` 链过去

**三道门槛全过，才配成为一篇正式笔记。**

---

## 四、一篇笔记的最低标准

每篇笔记**至少**包含以下三块中的两块（不需要模板字段，自然写就行）：

### 1. 场景（为什么写这篇）
不是一句话的 tags，而是一段话：我在做什么、遇到了什么问题、为什么需要搞清楚这件事。

### 2. 核心（我搞清楚了什么）
用自己的话写。如果涉及技术，写关键决策和为什么这么选，不是罗列概念。如果涉及认知，写我认同什么、反对什么、边界在哪里。

### 3. 连接（它跟什么有关）
链接到相关笔记，并写一句说明为什么相关。不是堆链接，是织网。

## 五、好笔记 vs 坏笔记：对照

### ❌ 坏笔记（搬运型）
```markdown
# RAG 简介
## 什么是检索增强生成？
检索增强生成（RAG）是指对大型语言模型输出进行优化，使其能够在生成响应之前引用训练数据来源之外的权威知识库...
```
问题：这是 AWS 文档的复制粘贴。读完之后，大脑什么都没做。下次遇到检索问题，还是不会用。

### ✅ 好笔记（经历型）
```markdown
## 场景：客户问了一个产品文档里有答案、但模型不知道的问题

用 RAG 解决：文档切 chunks → embedding 存向量库 → 提问时先检索 → 塞进 prompt

**关键决策**：chunk 用 512 tokens + 50 overlap。试过 256，太碎丢上下文。
**踩坑**：检索排序不对，加了 rerank 才解决。
**待验证**：换 BGE-M3 看看效果 → [[向量模型选型]]
```
区别：200 字，但每个字都是你的。有场景、有决策、有坑、有下一步。

## 六、工作流：从问题出发，不是从输入出发

### ❌ 旧流程（从外到内）
```
看视频/文章 → 觉得有道理 → 记下来 → 希望以后用得上 → 永远不会用上
```

### ✅ 新流程（从内到外）
```
遇到问题/产生疑问 → 去找答案 → 用自己的话写「我学到了什么」→ 链到相关笔记
                                                         ↓
                                              这篇笔记下次能帮到谁？
                                              → 帮到未来的自己 → 值
                                              → 帮不到任何人 → 删
```

### 具体步骤

1. **触发**：遇到真实问题、产生真实疑问、做出真实决策——这时才打开笔记
2. **写场景**：先写清楚"我遇到了什么"，再去找资料
3. **写核心**：查完资料后，用自己的话写"我搞清楚了什么"
4. **写连接**：搜已有笔记，把相关的链过来，写一句为什么相关
5. **写下一步**：这篇笔记指向什么行动？写出来。"继续研究"不算。

---

## 七、笔记的价值判断

一篇笔记**至少**承担以下一种作用，否则不值得存在：

- [ ] 帮我理解了一个问题
- [ ] 记录了一个经过思考的观点
- [ ] 支持了一个正在推进的项目
- [ ] 促成了一个明确的决定或下一步行动
- [ ] 成为文章、方案、复盘或其他作品的组成部分
- [ ] 保存了确实需要长期查阅的**个人**事实（账号、配置、个人经验）

**注意最后一条的"个人"二字。** 通用知识（"JUC 是什么"、"Spring IOC 原理"）搜索引擎比我记得好。我的笔记应该记**只有我知道的东西**：我的踩坑、我的判断、我的场景、我的决策。

## 八、目录和链接：各管什么

### 目录只管"存放"，链接管"关系"

| | 目录 | 链接 |
|---|---|---|
| **用途** | 存放——"这个东西放哪" | 思考——"这个跟什么有关" |
| **解决的问题** | 找到了不迷路 | 想起来有联系 |
| **类比** | 仓库的货架 | 大脑的神经元 |

**之前的错误：用目录解决"关系"的问题。**

PARA 试图用目录表达"这个项目跟这个领域有关"——但一篇笔记可能同时属于 3 个领域，于是不知道该放哪。最后分类越来越细，越来越累，然后放弃。

**正确做法：目录只按"状态"分，关系用链接解决。**

### 目录结构：只有 4 个顶层目录，不能再多

```
/                    ← 根目录：当前在思考的、正在用的
├── Archive/         ← 不活跃的：完成的项目、过时的内容（拍平，不分子目录）
├── Resources/       ← 长期参考：记账、年度报告、阅读笔记
└── Templates/       ← 写作提示模板
```

**规则：**

1. **根目录 = 当前关注点。** 根目录里的笔记就是我正在思考的东西。根目录本身就是我的 MOC——我关心什么，根目录就放什么。
2. **Archive 拍平。** 不分子目录（不要 `Archive/AI/`、`Archive/Programming/`）。不活跃的内容不需要细分，真要找的时候用搜索。少一层目录 = 少一次"该放哪"的决策。
3. **Resources 保留子目录。** 记账、年度报告、阅读笔记是长期结构化内容，子目录有意义。
4. **永远不要主动加新目录。** 只有当根目录某个主题下有 5+ 篇笔记且开始找不到时，才考虑——大概率一篇 MOC 就够了。

### MOC：长出来的，不是建出来的

**不要刻意建 MOC。** 刻意建的 MOC 会变成另一个 PARA——看起来对但用起来累。

**什么时候写 MOC：** 根目录某个主题下积累了 5+ 篇笔记，开始找不到东西了。

**MOC 写什么：** 不是链接列表，是**我对一个主题的判断**。

```markdown
# Agent 相关的思考

我现在在研究怎么给项目加一个智能客服。

## 我搞清楚了什么
- [[RAG 检索不准的问题]] — chunk 大小和 rerank 是关键
- [[向量模型选型]] — BGE-M3 中文效果好

## 还没搞清楚的
- 多轮对话的上下文怎么管理？
- 幻觉问题除了 RAG 还有什么解法？

## 我的判断
RAG 够用了，先别上 fine-tuning。
```

**MOC 的灵魂是"我的判断"那一栏。** 没有判断的 MOC 就是带链接的目录，没有价值。

### 链接怎么写

写新笔记时，问自己：**"这篇跟根目录的哪篇有关？"**

- 有关 → 加一个 `[[链接]]`，旁边写一句为什么相关
- 无关 → 它可能不该在根目录，放 Archive

**链接在写笔记时自然产生，不是在整理时刻意制造。** 不要专门花时间"建链接"。

## 九、反模式清单（看到就停）

以下行为出现时，**立即停止**，问自己"我在用整理逃避什么"：

- [ ] 花 30 分钟以上调整目录/标签/模板/插件
- [ ] 复制粘贴超过 3 行原文，没有加自己的话
- [ ] 给一篇笔记想了 5 分钟该放哪个目录
- [ ] 看到好文章就想"存下来以后看"
- [ ] 库里有 100+ 篇笔记，但最近一周没打开过任何一篇
- [ ] 为了"系统化"创建了一篇 MOC，但里面全是空链接
- [ ] 安装了一个新插件，但还没想好它能解决什么具体问题
- [ ] 给 Archive 建子目录分类（不活跃的内容不需要分类）
- [ ] 刻意花时间"补链接"（链接应该在写笔记时自然产生）
- [ ] 试图"建立知识体系"（知识体系是做事的副产品，不是目标）

## 十、定期复盘：只回答四个问题

每周/每月花 10 分钟，只回答：

1. **这周哪篇笔记真的被用到了？** → 这类笔记多写
2. **哪些笔记超过 3 个月没被打开过？** → 归档或删除
3. **当前最重要的项目/问题，库里有没有支撑？** → 没有就去写
4. **这周花在"整理"上的时间，有没有超过"写作"的时间？** → 超过了就停

---

## 十一、AI 操作本仓库的规则

当 AI 帮助操作本仓库时：

1. **不搬运。** 不把外部资料原文塞进笔记。要写就用自己的话，写场景、决策、踩坑。
2. **不膨胀。** 不主动创建大量新笔记、模板、索引、元数据。少即是多。
3. **不动结构。** 不大规模移动文件、重命名、重构目录，除非明确要求。
4. **保留人味。** 不把我的笔记改写成标准化语气。我的判断、口语、不完美表达才是价值。
5. **连接优先。** 新增内容时，优先找已有笔记建立链接，而不是创建孤立的新页面。
6. **可逆优先。** 能用小改动解决的，不做大重构。
7. **写之前问场景。** 帮写笔记时，先问我"这篇笔记的场景是什么"，不要直接动笔。

---

## 最终判断

每次准备收藏、整理、安装插件、修改模板或重构目录前，只问一句：

> **这件事会直接帮我下次遇到问题时多想一步吗？**

答不出来 → 默认不做。
